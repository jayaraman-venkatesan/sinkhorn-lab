## Exact behavior to preserve

The following is a reading of the pinned MIT-licensed solver source above. Let `a` be source supply, `b` target demand, `M[i,j]` the cost, and `r > 0` regularization. The source assumes normalized histograms; it does not comprehensively validate the documented preconditions.

1. Convert inputs to arrays and choose the numerical backend. Empty weight arrays become uniform vectors. For a single target, set `Mr = -M/r`, `u = 0`, `v = 0`, or use the supplied log scaling warm start; compute `loga = log(a)` and `logb = log(b)`.
2. Each zero-based iteration `ii` updates **all v first**, then **all u**: `v[j] = logb[j] - LSE_i(Mr[i,j] + u[i])`; `u[i] = loga[i] - LSE_j(Mr[i,j] + v[j])`.
3. The current plan is `T[i,j] = exp(Mr[i,j] + u[i] + v[j])`. At `ii % 10 == 0`, calculate the target marginal and its Euclidean residual `norm(T.sum(axis=0) - b)`; append that value to `log.err` when requested. Break only when that residual is strictly less than `stopThr`.
4. Defaults are 1,000 iterations and `stopThr=1e-9`. Exhausting the loop emits a warning when `warn=True`, then still returns a plan. `log.niter` is the **last zero-based index**, not the count; `niter=0` means one complete pair of updates. Logs contain final `log_u`, `log_v`, their exponentials `u`, `v`, and only the sampled errors, not a trajectory. Reject a zero iteration limit in a wrapper rather than inheriting the undefined final index.

The multi-target branch recursively solves target columns and returns transport costs, with different log structure. Treat that as additional scope rather than accidentally promising the full POT API. The basic `sinkhorn_knopp` uses `K=exp(-M/r)`, division and matrix products; on zero denominators or nonfinite scaling it warns, restores prior scaling, and exits. Its direct kernel can underflow at small regularization. The log solver avoids that kernel construction, but has **no equivalent numerical-error rollback** and no guarantee of convergence within the iteration budget.

Supporting operations are dense double arrays, row/column reductions, `exp`, `log`, stable log-sum-exp, Euclidean norm, and final weighted cost sum. POT's [NumPy backend](https://github.com/PythonOT/POT/blob/85113e9a380f5fcf684c50c73c1ff6a164a7366e/ot/backend.py) delegates LSE to SciPy and norm to NumPy. A C# implementation can supply these primitives without translating the backend machinery. For finite inputs use `m + log(sum(exp(x-m)))`; handle an all-negative-infinity slice explicitly. Consult [SciPy's LSE contract](https://docs.scipy.org/doc/scipy/reference/generated/scipy.special.logsumexp.html) and test the primitive independently. Copying SciPy implementation code would require separately checking its license; using the mathematical formula is a different activity.

## Boundary behavior and truthful diagnostics

Zero weights produce `log(0)=-Infinity`. With finite costs and positive total mass on both sides, zero coordinates can represent exactly zero rows/columns; the reference example below succeeds but emits a divide-by-zero warning. A recommended wrapper can remove zero support, solve on the positive support and restore exact zero rows/columns, explicitly documenting that preprocessing instead of claiming byte-for-byte POT behavior. Never replace zeros with arbitrary small positive mass. Reject negative/nonfinite weights, mismatched dimensions, unequal mass, all-zero mass, nonfinite costs, nonpositive/nonfinite regularization, and invalid budgets/tolerances. These are proposed wrapper guarantees, not existing POT validation.

Very small `r` can cause slow convergence, cancellation, overflow in `M/r`, or underflow when materializing `T`. Exponentiated scaling diagnostics can overflow even while log scalings and the plan are usable. Very large `r` weakens the cost preference; for normalized masses the entropy-dominated limit is `a b^T`. Report finite-value checks, both source and target residuals (L1 and/or infinity norm in addition to POT's stopping L2), total mass, iterations executed, and an explicit convergence/exhaustion/numerical-failure status. A final diagnostic does not silently change the sampled stopping rule. If epsilon scaling or another remedy is later added, label it as a different solver mode.

Keep three quantities distinct: transport cost `sum(T*M)`; regularized objective `sum(T*M) + r*sum(T*log(T))`, with `0 log 0 = 0`; and a debiased Sinkhorn divergence requiring self terms. POT's `sinkhorn2` returns the first quantity despite solving the regularized problem. An unfinished, marginally infeasible iterate is not a valid completed transport solution or an exact Wasserstein distance. These definitions are explicit in the [pinned solver](https://github.com/PythonOT/POT/blob/85113e9a380f5fcf684c50c73c1ff6a164a7366e/ot/bregman/_sinkhorn.py) and the [divergence paper](https://proceedings.mlr.press/v89/feydy19a.html).

For the paired beginner Markdown/TypeScript lessons, a read-only observer can copy `u`, `v`, and derived plans after the v update and after the u update. Show actual versus requested supply/demand: the v step enforces columns; the following u step enforces rows and may disturb columns. Keep the update order, arithmetic, and stopping checks unchanged; separate zero-based solver index, completed update-pair count, and animation frame number. Trace collection must neither mutate arrays nor round solver state. A later animation that gradually ships the final plan is **shipment playback**, not Sinkhorn iteration; its remaining inventory is a playback quantity. This recommendation follows the actual update equations, not an upstream tracing API.

Every case below used float64, `ot.bregman.sinkhorn_log(..., numItermax=1000, stopThr=1e-9, log=True)`. No C# implementation or cross-language verification exists yet.

For future fixtures, save exact inputs, package/runtime versions, all explicit parameters, final plan, log scalings, sampled residuals, `niter`, warnings/status and both cost conventions. Add asymmetric rectangular cases, repeated costs, warm starts, small positive weights, nonconvergence, and invalid-input wrapper cases. Capture iteration fixtures from an instrumented copy of this pinned source, then verify its final result against the untouched wheel before treating the trace as an oracle.

Suggested starting acceptance for small, well-conditioned normalized float64 fixtures: elementwise `abs(actual-reference) <= 1e-12 + 1e-9*abs(reference)`, costs under the same rule, and both marginal L1 residuals below `1e-8` for converged examples. These are **proposed test tolerances, not measured C# accuracy guarantees**. Test checkpoint indices/status explicitly on cases safely away from the threshold; floating reduction differences can shift threshold crossings. Compare plans before potentials because a compensating constant shift of log scalings leaves the plan unchanged. For tiny entries use absolute tolerance; for extreme cases assert appropriate failure/nonconvergence instead of relaxing tolerances until they pass. Trace enabled/disabled runs must produce the same computation and result.

## Existing C# options and resolution

[EmdFlat](https://github.com/sinshu/emdflat) identifies itself as a C# port of Rubner's EMD implementation. [NumFlat's EarthMoversDistance API](https://github.com/sinshu/numflat/blob/4d5d3ededce92f84d65a3e8b1fd1aa155c2a69fb/NumFlat/Distributions/EarthMoversDistance.cs) exposes distance and flow via EmdFlat and a maximum iteration count. Those inspected APIs provide a useful unregularized EMD comparison, but do not establish equivalence to this entropic, log-domain solver or its iteration trace. No ecosystem-wide absence claim follows from this bounded check; assess dependency licensing and mass/cost conventions separately before reuse.
